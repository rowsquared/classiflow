## Assessment

The existing architecture is suitable for incremental improvement. A single
Next.js application, Prisma, PostgreSQL, and an optional AI service do not need
to be replaced to make this product dependable. The urgent work is enforcing
security and data rules consistently on the server.

**I would not treat this baseline as ready for unrestricted public deployment.**
Several destructive application APIs have no authentication checks. Other APIs
require a session but permit writes outside the user's assigned records. These
are concrete implementation gaps, not merely missing security documentation.

There are useful foundations to preserve: hashed passwords, transactional writes
in important workflows, separation of suggestions from human labels, indexed
relationships, a non-root container user, no published production database port,
and a recently added CI smoke test and production deployment gate.

## Most consequential confirmed findings

### 1. Application API access control is incomplete

[Middleware](../../middleware.ts) explicitly passes API requests through.
An admin-only page therefore does not protect its API. These route files contain
no authentication guard at the reviewed commit:

| API | Methods without a guard | Source |
| --- | --- | --- |
| `/api/imports` | GET | [route](../../app/api/imports/route.ts) |
| `/api/imports/[id]` | DELETE | [route](../../app/api/imports/[id]/route.ts) |
| `/api/sentences/import` | POST, including commit with `dryRun=false` | [route](../../app/api/sentences/import/route.ts) |
| `/api/sentences/[sentenceId]/comments` | GET, POST, PATCH, DELETE | [route](../../app/api/sentences/[sentenceId]/comments/route.ts) |
| `/api/sentences/[sentenceId]/flag` | POST | [route](../../app/api/sentences/[sentenceId]/flag/route.ts) |
| `/api/taxonomies` | GET, POST | [route](../../app/api/taxonomies/route.ts) |
| `/api/taxonomies/[key]` | PUT, DELETE | [route](../../app/api/taxonomies/[key]/route.ts) |
| `/api/taxonomies/[key]/import` | POST | [route](../../app/api/taxonomies/[key]/import/route.ts) |
| `/api/taxonomies/[key]/restore` | POST | [route](../../app/api/taxonomies/[key]/restore/route.ts) |
| `/api/taxonomies/[key]/nodes` | GET | [route](../../app/api/taxonomies/[key]/nodes/route.ts) |
| `/api/taxonomies/active` | GET | [route](../../app/api/taxonomies/active/route.ts) |
| `/api/taxonomies/validate` | POST | [route](../../app/api/taxonomies/validate/route.ts) |

Public taxonomy reads may be an intentional policy choice; destructive writes
and record comments need an explicit access policy. The health probe and Auth.js
protocol handlers are separate intentional-public cases, not counted above.

The comments POST also attributes the new comment to `prisma.user.findFirst()`.
This creates false authorship. Single and bulk annotation APIs authenticate but
do not check record assignments. Assignment DELETE accepts supervisors without
restricting target records/users to their team. Fix these as one policy system,
including denied-request regression tests, rather than adding isolated checks.

### 2. Password reset and session revocation need server enforcement

[Admin initialization](../../scripts/init-admin.js), line 49, prints the initial
password. Compose and helper scripts supply known fallback passwords. If a
deployed environment used those defaults or exposed initialization logs, verify
exposure and rotate affected credentials; this review did not inspect real secrets.

[JWT callbacks](../../lib/auth.ts) refresh role/reset fields on a client session
update, not on every authenticated request. Password changes do not invalidate
existing JWTs through an application session-version check. Mandatory reset is
enforced by page redirects but omitted from business API guards. Deleted or
demoted users therefore require explicit lifecycle tests. The queue has an
additional fail-open case: its supervisor filter is only added if that user
still exists in the database.

### 3. Completion rules differ between write paths

[Bulk labeling](../../app/api/sentences/bulk-label/route.ts), line 139, sets
`submitted` even when the request only flags/comments or omits annotations.
[Single labeling](../../app/api/sentences/[sentenceId]/annotations/route.ts),
lines 123 onward, assumes the UI already enforced a complete leaf/unknown path.
It derives taxonomy from the first annotation without validating that all entries
agree. These rules must be checked by the server and shared by both paths.

The schema has an annotation lookup index, but no uniqueness constraint for a
sentence/taxonomy/level. Investigate concurrent replacement and stale browser
saves before adding a constraint; first decide whether multiple human annotations
are intended, then profile existing data and design a migration.

### 4. Green checks currently provide limited assurance

| Check performed locally | Result |
| --- | --- |
| `npm run typecheck` | Passed |
| `npm test` | 7 passed across 2 utility test files |
| `npm run lint` | Failed: 104 errors, 32 warnings |
| `npm audit --json` | 17 affected package entries: 4 critical, 10 high, 3 moderate |
| `npm ls --depth=0 --json` | Installed versions inspected; six extraneous native/WASM-related packages reported |

Audit counts include transitive and development packages and inherited severity;
they are not counts of independently exploitable application vulnerabilities.
Auth.js email/OAuth findings need provider-specific reachability analysis because
this application currently uses credentials. Vitest server findings also depend
on how the development server is exposed. Do not use `npm audit fix --force` as a
substitute for triage and compatibility testing.

Local runtime was Node 22.21.0/npm 11.6.2; CI and Docker specify Node 20 and the
manifest specifies npm 10.8.2. Local Next.js was 15.5.28, React/React DOM 19.3.1,
Auth.js 5.0.0-beta.29, Prisma/client 6.17.1, Vitest 3.2.4. Declared ranges and
installed versions differ. No lockfile records the deployment dependency graph.

Node 20 is now end-of-life, making the committed container/CI runtime a concrete
maintenance risk. [Node.js lifecycle reference](https://nodejs.org/en/about/eol).
The local Next.js version matches the 15.5 fix named in the October 14 advisory;
that does not establish deployed-image safety or clear other audit findings.
[Next.js security update](https://nextjs.org/blog/nextjs-security-update-october-14-2026).

## Recommended order

1. **Contain and close access gaps:** W01 and W02; add regression tests as part
   of each change. Verify whether current public deployments need temporary
   network access restrictions while fixes are prepared. Do not wait for a UI refactor.
2. **Establish a release baseline:** W03, W04, and W12. Inventory the actual
   deployed versions, secrets handling, ingress rules, backups, and release gate.
3. **Protect the work product:** W05 and W06, plus W08 metric corrections. Plan
   repairs of existing records separately from changes preventing new bad data.
4. **Make optional AI recoverable:** W07 before enabling multiple replicas or
   relying on unattended learning/training jobs.
5. **Optimize from measurements:** W08 tuning and W09, after policy and data
   semantics are stable. W10 proceeds in small changes alongside the relevant work.
6. **Reduce documentation burden:** correct W11's unsafe/inaccurate instructions
   early, then reorganize after the final runtime and deployment decisions.

W03 and operational discovery can proceed independently of W01. Coordinate
changes in shared files (`lib/auth*`, schema, annotation routes, CI, Docker,
AGENTS) so separate workstreams do not implement competing foundations.

## Limits of this review

This is a broad static review and planning baseline, not a penetration test or a
claim of complete security certification. It inventoried all 38 API route files
and examined the relevant authorization, labeling, import/export, AI, query,
client-state, deployment, and documentation paths. No production access, database
mutation, migration, deployment, full production build, browser journey, load
test, backup restore, container scan, or Git-history secret scan was performed.
The live proxy configuration and deployed images were not inspected. Performance
findings identify code patterns to measure, not measured latency regressions.

Before implementation, resolve the policy decisions called out in the briefs:
supervisor scope, comment ownership, independent annotation versus replacement,
conflict handling, expected dataset size, and recovery objectives. Discovery can
continue without those answers; changes whose behavior depends on them need an
explicit decision.
